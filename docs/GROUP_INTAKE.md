# 特定接單群組

預設接單來源群組僅為 `C0b0d5b3bce8b7d9cfe8eb2e133afeafa`，不再包含原群組 `C24304391da7434a2bc0ff5d1dd8c9413`。可用 `LINE_INTAKE_GROUP_IDS` 覆寫；部署時若已設定此變數，也必須改成新的單一 ID。這是來源群組，不會自動加入派單目的群組。原群組舊單因來源不再在允許清單，需人工處理後續群組通知。

只有訊息的 LINE mention metadata 真正標記 OTZ 主帳號，且 webhook 的 destination 是主帳號時，才會擷取同一則文字中的地址。單純打出 `@OTZ`、標記派單機器人、只標記但沒有地址，都不會建單。主帳號身分以 `LINE_CHANNEL_ACCESS_TOKEN` 查詢 bot info，快取一小時。

去除標記後沿用地址欄位解析，直接複製地址，不呼叫 Google 地點驗證或路線查詢。只有上車地址也可以建單，不再詢問是否叫車；沒有內容不建單。地址真實性由來源群組人員確認，座標留空、距離與時間為零，不代表已取得路線估價。成功建單後在來源群組只回覆「好」，不附建立訂單明細或尋車公告。此群組的一般文字不會落入自動叫車流程，但既有 `查群組ID`、`查ID` 指令保留。一般客人叫車與試算仍驗證地址。

訂單沿用既有資料表及派單程序，備註固定保存 `百回+30`，由 OTZ 主帳號送到 `LINE_DISPATCH_GROUP_ID` 設定的派單群組。顯示內容如下：

```text
訂單：01-XXXXX
60/20/2
上車地點：擷取的地址
下車地點：有提供才顯示此行
百回+30
```

此備註不更改既有試算費率；群組通知的標記所有人機制保持不變。

派單格式依特定流程固定保存的 `ride_details = 百回+30` 辨識。編號使用原訂單 ID，補至至少五位並冠上 `01-`，不是另一套流水號；結單同時接受 `01-XXXXX` 與既有 `OTZ-XXXXXX`。

新建特定單在派出前將來源群組保存於 `audit_logs`（`order.intake_source`），不需新增資料庫欄位。派單機器人收到結單標記後，沿用同段車牌四位數、顏色、1～2 位抵達時間或「準時」解析；順序不限。由 OTZ 主帳號的 LINE client 推送到保存的來源群組，而不是建單者私訊，也不是司機回報所在群組。來源群組必須仍在允許清單；無來源紀錄的舊單不猜測群組、不改送私人訊息。這類錯誤仍記錄在伺服器日誌，結單紀錄不回滾。群組 push 仍受 LINE 額度與主帳號群組成員資格限制。

回傳範例：

```text
提供司機車訊
訂單：01-00123
車牌/顏色/抵達時間：9820/白/15
感謝使用 OTZ 車隊。
```

派單群結單確認也使用 `01-XXXXX`；一般訂單仍私訊原客人，其他後台流程保持原樣。

## 特定群組取消

引用原建單訊息、真正標記 OTZ 並輸入「取消」，或輸入「取消 01-XXXXX」。取消解析優先於地址建單，包含取消字樣但格式不明確的內容會要求確認，不會當成上車點。新單的 `order.intake_source` 同時保存 `messageId` 與當時的 `dispatchGroupIds`。引用與明示單號同時存在時必須指向同一筆、同來源群組的單；無法唯一定位時不取消、不猜最新單。

pending 未接單、或已完成首次車訊回報但尚無抵達紀錄的單，可直接取消，不等待司機確認。已回報車訊時，使用第一筆 `order.dispatch_tag_complete.details.source` 找原接單司機與回報群組；在該群組用 textV2 user mention 真正標記司機，其他原派單群組仍收到取消公告。若原司機回報群組不在原清單，追加通知該群組。標記失敗不降級成普通文字冒充成功。通知內容為「訂單：01-XXXXX／此單已取消，請勿前往。／上車地點」。OTZ 在接單來源群組回覆取消成功；部分推送失敗時則明確提示人工確認，訂單仍維持已取消。

部署前須先套用 `database/upgrade_v5_5.sql`（並保留 v5_4 的唯一索引）。取消與抵達 RPC 鎖定同一訂單列：取消先完成則抵達被拒；抵達紀錄先建立則取消被拒、需人工處理，包含 pending 或送達不明的抵達通知。保留原 completed_at 與車訊稽核作為歷程，最新狀態改為 cancelled。資料庫 RPC 只允許 service_role 執行。此變更沿用特定群組的引用／單號取消入口，不擴大到其他後台操作。舊單缺少原派單群組或接單司機識別時需人工確認；不自動清理先前誤建的「取消」地址單。

## 第二階段抵達回報

部署此功能前必須執行 `database/upgrade_v5_4.sql`，建立抵達通知的唯一索引。第一階段仍保存 `order.dispatch_tag_complete` 與車訊；完成訂單再次被標記時，只接受獨立一行「抵達」（可同行標記機器人），不將「抵達時間」或「尚未抵達」當成抵達。

第二階段須有第一階段標記完成紀錄；一般訂單由 OTZ 私訊原客人，特定單回保存的來源群組，內容為「訂單：編號」及「司機已抵達。」。派單機器人回標記回報者，確認抵達已紀錄。第一階段尚未完成時，單獨抵達不會發出通知。

`order.dispatch_arrival` 唯一紀錄在送出前取得，避免跨機器人重複推送。狀態為 `pending`、`sent` 或 `failed_or_unknown`；送達不明時保留紀錄並由後台確認，不自動重送，以避免實際已送達卻重複通知。此紀錄表示第二階段，不另改既有訂單 completed 狀態。LINE 額度不足仍可能造成推送失敗。
